## 开场：项目理解

老师、同学们好，我汇报一下 SmartDoc 项目的数据调研和下一步数据方案。

我对项目的理解是：我们要研究一个本地优先的文档智能体。用户的 PDF、Word、Excel 等文档留在本地或受控环境，系统通过模型和工具完成阅读、检索、问答、总结、跨文档比较、表格计算和结构化导出，并能把答案指回原文页码或区域。第一阶段先用现有模型和 harness 搭建可演示的系统；后面再研究 SFT、Agentic RL 和执行流程优化。当前做的是研究原型，不是马上做手机端产品，也不是先追求某个公开榜单的最高分。

因此，数据工作要分清几件事：答案是否正确、证据是否找准、工具调用过程是否有效，以及整个任务的时间和资源成本。只准备问答题和答案，无法训练或评价一个会规划和调用工具的 agent。

## 调研范围与主要发现

我重点看了 2024 到 2026 年的长文档、多模态文档、检索 agent、工具调用、Agentic RL 和过程监督论文，也补看了 QASPER、FinQA、TAT-QA 等公开数据集的源论文。完整 PDF 和下载来源按主题放在仓库 `papers/` 目录，目录中的索引列出论文标题、年份、编号和本地文件名。

第一组对我们任务最直接：LongDocURL 把长文档理解、推理和证据定位放在一个 benchmark 里；MMLongBench-Doc 关注视觉长文档，而 2026 年的 V2 修订提醒我们，公开基准本身的答案和证据标注也要抽查；MMDocIR 侧重多模态长文档检索；MEBench 关注跨文档、多实体问答；DocAgent 和后续的 DocLens 展示了文档处理可以按工具或子任务组织成 agent 流程。这些工作给我们的启发是，系统评估不能只看最终答案，要把“没检索到证据”和“有证据但推理错了”区分开。

第二组是工具使用和 Agentic RL。τ-bench 强调 agent、工具和环境状态之间的多轮交互；ToolACE 和 ToolACE-DEV 提供合成工具调用数据的构造思路；Search-R1、R1-Searcher++、WebAgent-R1 等工作研究模型何时检索、如何交替执行和推理，以及怎样用可验证的任务结果提供奖励；TRAJECT-Bench 把评价对象从最终答案扩展到完整轨迹。给我们的核心启发是：静态 QA 文件不等于 RL 数据。Agentic RL 需要一个能重置、能重放、工具返回稳定的任务环境，以及每一步的 action、observation、奖励和终局判定。

第三组是 CoT 和过程监督。PRM800K、ProcessBench 说明过程信号可以帮助定位推理错误，但它们不是文档工具 agent 的现成训练集。我们的 CoT 数据不应该只是让教师模型写一段很长的理由，而应该记录可审计的过程：简短计划、工具名和参数、工具返回、证据 ID、必要的计算或字段校验、以及继续/停止/拒答的判断。工具返回由程序环境产生，不能让教师模型编造；对于私有长思维链，不把它作为必要标签。

## 现有开源数据怎么用

现有数据可以让我们快速建立基线，但每个集合覆盖的能力不同。

QASPER 是科学论文问答，包含不可回答场景，适合做论文文档问答基线。FinQA 和 TAT-QA 是财务文本与表格推理，适合测试表格证据和计算。DocVQA、DUDE 可以补充视觉文档问答和文档类型覆盖。LongDocURL、MMLongBench-Doc/V2、MMDocIR 和 MEBench 可用于长文档定位、检索和跨文档能力的外部评估。τ-bench、GTA 和 TRAJECT-Bench 可用于借鉴通用工具交互与轨迹评价方法，不能直接替代我们自己的文档 benchmark。

许可要按数据文件逐项核验。当前检查到 QASPER 的 Hugging Face 卡标了 CC-BY-4.0，FinQA 与 TAT-QA 的 GitHub 仓库标了 MIT，但仓库代码许可不一定自动覆盖原始财报、论文图表或所有派生文件。DocVQA 等数据可能还要遵守官方申请和使用条款。建议第一轮把公开测试集只用于评测，不并入训练；下载后记录来源、版本、许可和校验和，不把原始数据镜像进我们的 GitHub 仓库。

## 我建议的数据分阶段方案

**第一阶段：评测集和系统基线。** 先组合公开基准，内部再做一套小型留出集。首轮目标是 600 到 1,000 个任务，覆盖单文档问答与抽取、长文档多跳问答、表格计算、多文档比较、页码/区域定位、不可回答和冲突场景、结构化导出。所有标注至少包含参考答案、支持证据、页码或区域、答案判定规则、来源和许可。训练、开发、测试按文档或模板切分，不能只随机切问题，否则同一份文档会泄漏到两边。

这里开源集主要承担外部基线和评测。我们自建的部分是少量、可公开的合成文档任务和私有留出题，尤其是测试解析失败、证据冲突、拒答和提示注入的样本。评测题不能混到后面的 SFT/RL 训练集。

**第二阶段：SFT 示范数据。** 首轮建议先做 500 到 1,000 条人工或半自动种子，再扩到 3,000 到 8,000 条高质量轨迹；效果稳定后再增加到几万量级。数据覆盖任务澄清、选工具、填参数、检查工具返回、定位证据、计算、格式化答案、失败恢复和拒答。文档来源优先选自制合成文档和明确允许训练的公开训练 split。ToolACE 可以帮助设计通用函数调用格式，但不能代替文档域数据。合成时，教师模型只生成候选问题、答案或简短决策说明；页码和证据必须由解析/检索工具真实返回，再通过程序校验和人工抽样检查。

**第三阶段：Agentic RL 交互轨迹。** 这一阶段需要我们自建文档任务环境。每个 episode 固定一组文档和用户请求，开放受控的解析、页检索、表格读取、计算等工具；环境可重置，返回可重复。任务从自建合成文档和许可允许的训练材料中生成。每条 rollout 记录每一步的 observation、tool/action、参数、工具结果、过程标签、奖励、耗时、终止原因和模型/工具版本。奖励至少分成终局答案正确、证据有效、工具动作正确、是否正确停止/拒答和调用成本。公开的 web agent RL 轨迹只能借鉴方法，不能直接当成我们的文档 RL 数据。

**第四阶段：过程评估数据，按需扩展。** 先对 500 到 1,000 条成功和失败轨迹做人工步骤标注，找出第一个错误动作，并标注工具是否选对、证据是否有效、是否应该继续或停止。可以从同一任务下构造成功/失败轨迹对，做偏好评估。如果这些标签的一致性和对任务成功率的相关性足够好，再训练过程奖励模型；不建议现在就先造大量自由文本 CoT 或先训练 PRM。

## 数据格式和质量控制

建议统一使用 UTF-8 JSONL。文档二进制不嵌进每一行，保存在受控目录中，记录 `doc_id`、URI 和 SHA-256。问答标注包含 `question`、`target.answer`、`evidence[]`；SFT 用 `messages[]` 分开保存 assistant tool call、tool observation 和最终回答；RL 用 `trajectory[]` 保存逐步 action、observation 引用、step label 和 reward。证据要有稳定 ID，页码和 bbox 用归一化坐标，表格任务另存行列/单元格坐标。仓库的 `data/examples/README.md` 有最小样例。

质量上先让两位标注者试标 100 条，修改指南后再扩量。严格按文档源切分，做重复和泄漏检查；对不可回答、相互冲突、恶意指令、OCR 噪声等高风险样例人工复核。评测时分别报告答案正确率、证据召回与定位、引用支持率、拒答准确率、任务完成率、工具调用数和延迟，而不是只报一个总分。

## 接下来三周的交付建议

第一周完成数据/论文矩阵、许可记录和工具 schema 对齐；第二周完成 100 条双人试标、标注指南和基线任务；第三周交付 600 到 1,000 条评测集方案、SFT 生成与审核方案，以及 RL episode 和奖励定义。正式扩数据前，先让系统跑通 50 到 100 个可重放 episode，验证日志和奖励是否可信。

## 最后总结：我们到底要哪些数据

1. **评测阶段：先用开源数据。** 首选 QASPER、FinQA、TAT-QA、DocVQA/DUDE 和 LongDocURL、MMLongBench-Doc/V2、MMDocIR、MEBench；严格核验许可，测试 split 只评测。另建 600–1,000 条文档隔离的内部留出集。
2. **SFT 阶段：开源训练 split + 自建数据。** 复用许可允许的 QASPER/FinQA/TAT-QA 等训练部分做基线；主体示范数据由我们用自制合成文档、工具实际执行结果和人工审核构造，目标先 3,000–8,000 条。
3. **Agentic RL 阶段：主要自建。** 自己构造可重置的本地文档工具环境、任务和多步 rollout；公开论文只借鉴环境/奖励方法，不把通用 web-agent 轨迹当文档 RL 数据。
4. **过程奖励阶段：自建标注，按需训练。** 对自有 RL 轨迹标工具动作、证据、继续/停止和首个失败步骤；先做 500–1,000 条人工核验，再决定是否训练 PRM。

一句话概括：**开源数据负责起基线和外部评测；文档 agent 的高质量 SFT 示范、可重放 RL 轨迹和过程标签需要我们自己构造。**
