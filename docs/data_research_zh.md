# SmartDoc 数据调研与构建方案

更新：2026 年 11 月 18 日。本版集中讨论 7 项与当前工作最相关的研究，已核对本地 PDF 的摘要和相关方法、数据、评估章节。下文区分原文做法和我们的方案；数量及时间是试运行建议，尚未通过实验验证。

阅读说明：每篇文献下都先写明数据集是否直接进入 SmartDoc，再区分“论文原文示例”和“SmartDoc 改造示意”。除特别标注外，示例均来自论文 PDF 中的图、表、算法或附录，不是我们另造的论文样本。

## 项目问题

我们希望本地或受控环境中的文档智能体完成问答、抽取、总结和比较，并返回可核验的证据。当前先搭建不训练的原型，数据侧要分别评估答案、证据、工具执行过程和成本；后续才用验证过的数据研究 SFT 和智能体强化学习。

## 重点文献：做了什么，对我们有什么用

### 1. LongDocURL：按任务和证据类型拆分评测

[本地 PDF](../papers/pdfs/documents/2025_2025.acl-long.57_LongDocURL.pdf)｜[在线原文](https://aclanthology.org/2025.acl-long.57/)｜2025｜第 3 节、表 2、图 3。

**做了什么。** 构建长文档基准，将任务分为理解、数值推理和跨元素定位，按证据类型、单页或跨页等细分为 20 个子任务。最终 2,325 个问答样本覆盖 396 份文档、超过 33,000 页，约 52.9% 的问题涉及多页证据；证据包括正文、版面元素、表格和图形。

**我们是否使用这篇的数据。** 当前不直接拿 LongDocURL 训练 SmartDoc；先把它作为外部评测候选。是否下载并纳入正式测试，要先核对项目页和源文档许可。我们使用的是它的任务划分和评测思路，不把它当作工具调用或 SFT 轨迹集。

**数据怎么做。** 先筛选 PDF，解析出文本、类型和位置；通过多轮模型生成候选问答与证据；自动检查相关性、格式和忠实性，最后人工对照原始页面复核和修正。作者指出自动检查可能遗漏视觉结构，因而需要人工复核。

**论文原文示例（Figure 2）。** 论文给出的理解题是：`What are the four main areas of translational and applied research that used the most animals in 2018?` 标准答案是 `Animal diseases and disorders; Human cancer; Human nervous and mental disorders; Human infectious disorders`，证据跨第 37 页图和第 38 页表。数值推理题是：`Where is the majority of non-human primates sourced from in 2018?`，选项为 `A Asia / B Africa / C EU / D American`，标准答案为 `A`，证据在第 24 页图。跨元素定位题给出“2018 年 EU-28 和挪威使用 1,080 万只动物”的段落，要求在文档标题中找对应章节，标准答案是 `IV.2.1.1. Main categories of scientific purposes`，证据为第 29、30 页标题和段落。这里可以直接看出它同时覆盖正文、图、表、跨页证据，但它的“定位”是找章节关系，不等于 bbox 或逐字坐标定位。

**我们借鉴什么。** 用“任务类型 × 证据类型 × 单页/跨页”组织评测。每题保存答案、文档 ID、支持页和证据类型；模型可以提议题目，但页码与内容要回到原文核验。先抽少量样例验证系统能否读取，再考虑扩大。

**边界。** 论文的定位包括由段落找到对应标题等跨元素关系，并不等同于逐字或坐标框定位；我们要另行设计页码、区域或单元格指标。表 2 仅有 2 条不可回答问题，不能单独衡量拒答。它是评测基准，不提供我们需要的工具调用训练轨迹；下载及许可需从[项目页面](https://github.com/dengc2023/LongDocURL)核对。

### 2. QASPER：答案和支持证据分开标注

[本地 PDF](../papers/pdfs/datasets/2021_2105.03011_QASPER.pdf)｜[在线原文](https://arxiv.org/abs/2105.03011)｜2021，作为基础数据集保留｜第 3–4 节。

**做了什么。** 针对 1,585 篇自然语言处理论文构建 5,049 个问题。提问者只看标题和摘要提出信息需求，另一组标注者阅读全文回答并选择支持证据。答案包括抽取式、生成式、是/否和不可回答。原文按论文切分训练、验证、测试，分别评估答案 F1 和证据 F1。

**我们是否使用这篇的数据。** 可以直接使用许可允许的训练/验证划分，先作为普通文档问答和证据评价基线；测试划分只用于评测，不转成工具调用轨迹。它不是合同、表格或 PDF 坐标数据，所以不能替代 SmartDoc 自建数据。

**论文原文示例（Figure 1）。** 论文展示的问题是 `Which retrieval system was used for the baselines?`。提问者只看论文标题和摘要提出问题，回答者需要回到全文；图中标出了分散在第 3、4 节的支持证据。论文还列出不同答案类型的问题，例如 `What datasets do they use?`、`What other political events are included in the database?`、`What five dialogue attributes were analyzed?`，数据中同时存在抽取式、生成式、Yes/No 和不可回答答案。这个例子说明答案文本和支持证据必须分开记录，答对问题但选错证据时，两项 F1 不会混成一个分数。

**我们借鉴什么。** 先用它验证“问题—答案—证据”链条。记录分别保存 `answer`、`answerable`、`evidence[]`，允许多个参考答案和证据；按文档切分，避免同一文档的问题跨训练和测试。合同或表格任务需另行验证泛化。

**边界。** 数据面向 NLP 学术论文，证据是段落、表格或图等，不能假定全部直接带 PDF 页码或坐标，也不包含完整工具交互轨迹。训练和再分发前核对[数据卡](https://huggingface.co/datasets/allenai/qasper)及源文档条款；测试集不参与训练。

### 3. DocAgent：先看结构，再按需读取和复核

[本地 PDF](../papers/pdfs/documents/2025_2025.emnlp-main.893_DocAgent.pdf)｜[在线原文](https://aclanthology.org/2025.emnlp-main.893/)｜2025｜第 3–5 节。

**做了什么。** 构建长多模态文档多智能体框架：先把章节、表格和图表等组织成树状大纲，为元素提供标识及页码信息；执行智能体通过交互接口按需获取内容；审查智能体用补充信息核查答案，经验存入记忆。论文在长文档基准上实验并分析组成模块。

**我们是否使用这篇的数据。** 不直接使用 DocAgent 的数据或生成轨迹；论文使用的是 MMLongBench-Doc（135 份长 PDF）和 DocBench（229 份长文档、1,102 个问题）做实验。SmartDoc 只参考它的系统流程、工具组织和日志字段，不能把论文中的演示轨迹当成可直接训练的 SFT/RL 数据。

**论文原文示例（附录 A.6）。** 用户问题是 `From this report, which subgroup among Hispanics has gained most confidence from 2008 to 2015?`。Actor 先根据大纲定位到 `9.1.1 Most key Latino demographic subgroups see gains in personal finance ratings since 2008`，调用 `get_section_content(section_id: 9.1.1)`；返回内容指出 18–29 岁 Latino 的正面财务评价从 2008 到 2015 增加 27 个百分点，Actor 据此作答。Reviewer 随后调用 `get_table_image(table_id: 0)` 检查图表，并确认答案。论文说明 Actor 最初只看文字时可能答错，Reviewer 交叉查看图像后纠正；Memory 再保存这次经验。这个案例具体展示了“先看 outline → 取章节 → Reviewer 取补充模态证据”的流程。

**我们借鉴什么。** 设计文档目录和工具日志：目录保留章节、页码、元素 ID；记录“查看目录 → 搜索 → 读取证据 → 作答/复核”的实际执行。比较两篇报告时，分别定位对应章节并留证据，再比较结论。每步保留参数、实际返回和证据 ID，便于定位错误。

**边界。** 原文是系统方法，不是现成的文档 SFT/RL 轨迹集；多智能体和审查会增加调用与延迟，是否适合小模型需与单智能体、无审查方案对照。它没有证明我们的端侧资源约束已解决。

### 4. ToolACE：合成工具示范并分层检查

[本地 PDF](../papers/pdfs/agents/2024_2409.00920_ToolACE.pdf)｜[在线原文](https://arxiv.org/abs/2409.00920)｜2024｜第 2 节。

**做了什么。** 作者合成 26,507 个 API 的工具池，用用户、助手和工具角色生成对话，覆盖单次调用、并行调用、依赖调用和无需调用；使用目标模型评估并调整难度，再以规则和模型两层检查过滤。论文称部分数据和模型公开，具体版本及许可需核验。

**我们是否使用这篇的数据。** 不直接使用 ToolACE 的通用 API 对话训练 SmartDoc。它的数据和工具不是 PDF、表格或 OCR 工具；我们只参考它的工具池构造、四类对话覆盖、难度自适应和双层校验流程。若许可允许，可把公开数据仅作为通用函数调用基线，不能当作文档轨迹。

**论文原文示例（Figure 1 与第 2.2 节）。** ToolACE 的 API 上下文树用真实文档抽取功能节点，论文举的功能例子包括 `get the weather forecast`、`get the stock price` 和 `send an email`。随后从 API 池抽样，由 User Agent、Assistant Agent、Tool Agent 角色扮演，生成四类对话：single、parallel、dependent 和 non-tool。Assistant 的动作不只有调用 API，还可以请求补充信息、总结工具反馈或直接回答；Tool Agent 根据工具描述和参数模拟返回。最后先做 Rule Checker（类型、必填参数、格式和值约束），再做 Model Checker（语义一致性），并可人工复核。这个原文流程是我们要借鉴的构造模板；其中 Tool Agent 的返回是模拟结果，不能直接替代 SmartDoc 的真实 PDF 工具返回。

**我们借鉴什么。** 固定 SmartDoc 的实际工具清单后，分别生成单次检索、跨页依赖、跨文档比较、无需工具和需要澄清的候选任务。先查工具名、必填参数、JSON 结构，再核查调用与用户需求、证据、答案是否一致；同时覆盖失败和重试，不只构造理想路径。

**边界。** 原文的工具角色可由模型模拟返回。为减少虚构页码和结果，我们拟用实际工具返回替换模拟观察，再检查证据并人工抽样；这是我们的改造，不是 ToolACE 已验证真实 PDF。通用函数调用数据不能直接替代文档轨迹。

### 5. Search-R1：根据检索反馈决定下一步

[本地 PDF](../papers/pdfs/agents/2025_2503.09516_Search-R1.pdf)｜[在线原文](https://arxiv.org/abs/2503.09516)｜2025｜第 3–4 节。

**它要解决什么问题。** 一些基础 RAG 流程只在作答前检索一次；遇到多跳问题时可能缺少必要信息。Search-R1 研究的是让模型在生成答案的过程中自主决定是否搜索、搜索什么、拿到结果后是否继续搜索。

**它具体怎么做。** 论文把搜索引擎放进 RL 环境。模型生成搜索查询，环境返回检索结果，模型再继续推理、再次搜索或回答；因此一条轨迹是“思考—搜索—读结果—再思考—再搜索/回答”，而不是一次固定的检索。训练使用 PPO 或 GRPO，从 NQ、HotpotQA 等问答训练集采样问题，用规则计算最终答案的 exact match 作为结果奖励。作者没有训练过程奖励模型，也没有把格式奖励作为主要信号。

**我们是否使用这篇的数据。** 不直接使用 Search-R1 的 NQ、HotpotQA 或七个评测集来训练文档智能体；它们只能作为检索型 RL 的方法参照。SmartDoc 需要把搜索环境替换为本地解析、检索、页读取和表格读取环境，并重新制作任务、证据和奖励。

**最关键的技术点。** 检索结果是环境提供的 token，不是模型应该学习生成的 token。作者在策略损失和 KL 损失中遮蔽这些 token，避免模型因为复制检索文本获得错误梯度；消融实验显示，使用检索 token 遮蔽的版本在多个数据集上优于不遮蔽版本。论文还比较 PPO 与 GRPO，报告 PPO 在长时间训练中更稳定，而二者最终性能接近；在七个问答数据集上，相比同设置的 RAG 基线，Qwen2.5-7B 和 3B 都有明显提升。

**论文原文示例（Table 9）。** 问题是 `Curious is a women’s fragrance by a singer born in what city and state?`，标准答案是 `McComb, Mississippi`。Search-R1 的轨迹依次为：先输出 `<search> Curious fragrance information </search>`，检索结果识别出歌手是 Britney Spears；再输出 `<search> Britney Spears birthplace </search>`，结果给出她出生于 McComb, Mississippi；最后再检索 `<search> McComb, Mississippi location </search>`，然后在 `<answer>` 中回答。每次检索结果包在 `<information>...</information>`，模型自己的思考包在 `<think>...</think>`，最终回答包在 `<answer>...</answer>`。这就是论文真实展示的多轮“生成查询—接收环境观察—继续生成”例子；训练时检索返回 token 被 loss masking，不要求模型学习复制搜索结果。

**我们具体借鉴什么。** 把搜索引擎换成 SmartDoc 的本地工具：parse_document、search_text、read_page、read_table、calculate。**SmartDoc 改造示意：** 如果问题是“两份合同的续约期限有什么不同”，模型应分别搜索“续约期限”，根据返回决定是否读取具体页面；只找到合同 A 时继续检索合同 B，而不是直接回答。我们要记录完整动作序列、每次查询、工具返回、最终答案和证据页。这个合同例子是我们的落地示意，不是 Search-R1 原文样本。

奖励建议先做最小版本：最终答案正确且格式合法为主奖励；引用的页或单元格确实支持答案再加奖励；无效调用、重复检索和循环给小惩罚。等环境能稳定重放后，再比较“只有终局奖励”和“加入工具选择、证据、停止等过程奖励”。这比一开始直接设计复杂 PRM 更容易确认问题来自模型还是环境。

**边界。** 检索语料和奖励不能直接照搬到 PDF/表格；工具结果遮蔽需由训练框架针对具体 token 和损失掩码实现、测试。答案正确不代表工具过程必然合理，仍需独立评测轨迹。

### 6. TRAJECT-Bench：评测工具执行过程

[本地 PDF](../papers/pdfs/agents/2025_2510.04550_TRAJECT-Bench.pdf)｜[在线原文](https://arxiv.org/abs/2510.04550)｜2025｜摘要及基准构造/评估章节。

**它要解决什么问题。** 只看最终答案无法知道 agent 到底会不会用工具：它可能没有调用必要工具、工具顺序错误、参数不合法，却碰巧凭记忆答对；也可能工具轨迹基本正确，只在最后一步表达失败。TRAJECT-Bench 因此把工具使用轨迹本身作为评测对象。

**它具体怎么构造。** 作者整理 1,228 个可执行工具和 5,670 个问题，工具来自多个真实领域并使用生产式 API 约束。先人工或按模板构造工具轨迹，再生成与轨迹对应的用户问题。轨迹有两种结构：互不依赖、可以并行的调用；以及后一步参数依赖前一步返回的顺序调用。每条轨迹覆盖约 3 到 10 个以上工具。相同轨迹配两种问题：直接明确说出需求的简单问法，以及需要理解用户意图的自然或隐含问法。

**我们是否使用这篇的数据。** 不直接使用 TRAJECT-Bench 的旅行、金融等通用工具数据训练 SmartDoc；它的工具返回和任务不包含我们的 PDF 页码、表格或 OCR 证据。我们只参考它的轨迹构造方式和轨迹级评测指标。

**它怎么评分。** 最终答案之外有四类轨迹指标：Trajectory Exact Match 比较预测和标准轨迹中的工具名称；Trajectory Inclusion 衡量标准工具有多少被预测轨迹包含；Tool Usage 比较工具参数；Trajectory Satisfy 用评判模型判断轨迹是否足以完成问题。并行与顺序任务的轨迹表示不同，顺序约束需要结合具体评测实现核对，不能把 Inclusion 一概说成顺序正确率。作者还分析工具数量、工具相似度和问题难度带来的失败。

**论文原文示例（Figure 1 与附录）。** 顺序轨迹示例是 `GetAllIATA -> airportInfo`：前者返回机场 IATA code，后者把这个 code 作为输入；论文还画出 `city -> hotel location -> hotel detail` 的依赖链。并行轨迹则把航班搜索和酒店搜索组合成旅行规划。同一条轨迹会配一个直接的 simple query 和一个含蓄的 hard query，例如把“按 review score 排序”说成 `hotels with good record`。附录中的真实请求是：`I’m planning a trip to London from Oct 10 to Oct 17 in 2025...`，要求同时查询 Booking.com、Hotels.com、酒店星级、取消政策和近期照片。由此可见，Inclusion 只是检查必要工具是否被覆盖，参数和依赖顺序仍需单独检查。

**我们具体借鉴什么。** SmartDoc 不应该只记录“回答对/错”。我们可以为每个文档任务定义必要条件：是否调用正确的解析器、是否查询了正确文档、页码参数是否有效、是否读取了支持答案的证据、跨文档比较时是否先分别取证。对同一任务写一个直接问法和一个自然问法，测试模型是否只会照关键词选工具。由于文档任务通常有多条合理路径，Exact Match 只能作诊断指标，主指标应是工具参数合法、必要证据获取和最终答案或引用是否成立。

**边界。** 原基准是通用工具任务，不能直接代表文档页码、表格或解析质量；模型评判应与人工标注对照。我们尚未验证其数据是否适合直接复用。

### 7. ProcessBench：先标最早错误，再考虑过程奖励

[本地 PDF](../papers/pdfs/process/2024_2412.06559_ProcessBench.pdf)｜[在线原文](https://arxiv.org/abs/2412.06559)｜2024｜第 3–4 节。

**它要解决什么问题。** 许多过程奖励模型只给每一步打分，或者只看最终答案，不能直接回答“这条解题过程第一次错在第几步”。如果后面的步骤建立在错误前提上，继续给后续步骤打分也会混淆。ProcessBench 把任务简化成明确的过程诊断问题：给定完整解题过程，找最早错误；如果没有错误，输出 -1。

**它具体怎么做。** 数据共有 3,400 条测试样本，来自 GSM8K、MATH、Olympiad 等不同难度的数学题。每个样本包含题目和按步骤切开的完整解答，专家标注最早出错步骤索引；错误包括计算、逻辑、概念和完整性错误，但最终标签只需要步骤位置，不强制每条都标错误类别。困难样本由多名数学背景标注者复核，并设置资格测试和标注教程。论文特别指出，正确最终答案的解答中也可能有中间错误，不能用最终答案替代过程标签。

**我们是否使用这篇的数据。** 不把 ProcessBench 的数学样本直接用于 SmartDoc 的 SFT 或 Agentic RL；它只提供“首个错误步骤”这一过程评测任务和多标注者质检机制。SmartDoc 的过程样本必须来自真实文档工具轨迹。

**论文原文示例（Figure 2）。** 题目是求 `n`，满足 `0 <= n <= 180` 且 `cos(n°) = cos(568°)`。第 0 步利用余弦的 360° 周期把 568° 化为 208°；第 1 步得到 `cos 568° = cos 208°`；第 2 步错误地声称余弦关于 180° 对称并写出 `cos θ = cos(180° - θ)`；后续由此得到 `cos 28°` 和答案 28。论文标签为 `2`，表示从 0 开始计数的第 2 步是最早错误；无错误样本标签为 `-1`。论文的标注流程是先统一步骤粒度，每条样本初始由 3 名专家标注，出现分歧时最多增加到 5 名，仍不能形成 3 人一致则丢弃，约 30% 样本因此被丢弃。

**它得出什么结论。** 论文发现，已有 PRM 在超出 GSM8K/MATH 的难题上泛化较差；通用模型作为逐步批评者有时比现成 PRM 更好，作者用 PRM800K 做简单微调也能得到有竞争力的结果。错误常出现在较早步骤，难题中即使最终答案正确也存在过程错误。这说明过程评测应单独做，“最终答对”不能直接当作“每一步都对”。

**我们具体借鉴什么。** SmartDoc 的过程标注可以采用同样的首错任务。给标注者一条完整轨迹，从第 0 步开始判断：工具是否选对、参数是否指向正确文档或页面、返回结果是否被正确理解、证据是否足以支持下一步；遇到第一处明确错误就停止并记录 first_error_step。如果信息不足而不能判断，记录 uncertain，不要强行贴正确或错误。之后才考虑把每步标签转换成过程奖励或偏好对。

**SmartDoc 改造示意（不是 ProcessBench 原文样本）。** 第 0 步正确选择 `search_text`，第 1 步搜索到合同 A 的续约条款，第 2 步把页码 7 误写成合同 B 的页码；即使最后碰巧答对，第 2 步也应标为首个明确错误。如果第 1 步工具返回为空，后续是否应该重试要依据任务和工具状态判断；不能因为最终答案错就自动把第 1 步标错。

**边界。** 它评测数学推理，不能直接作为文档智能体过程训练集；多条可行路径、工具故障和信息不足会增加首错判断难度。先验证标注可靠性，再决定是否训练过程奖励模型。

## 数据方案：来源、格式和用途

| 阶段 | 需要的数据 | 来源和构造 | 最小记录 | 当前动作 |
|---|---|---|---|---|
| 不训练原型评测 | 问题、参考答案和证据；包含可回答、不可回答、跨页题 | **QASPER：许可允许时直接使用**测试集验证文本问答；**LongDocURL：许可核验后仅作外部评测候选**；另**自建**少量文档留出题 | 文档 ID、问题、答案/不可回答、证据文本和页码、评分规则 | 核对许可与下载方式，先抽 20–50 题跑通；LongDocURL 定位不等同坐标定位 |
| SFT | 工具调用、观察、最终回答和证据组成的示范 | **自建为主**：合成或授权文档、教师候选、实际工具执行、自动和人工校验；允许使用的 QASPER 训练划分可作普通问答基线 | 对话、工具 schema/参数、真实工具结果、证据 ID、答案、版本 | 先做 50–100 条试验样例并复核；开源 QA 不自动变成轨迹 |
| Agentic RL | 可重置任务、工具环境、参考答案及多条交互轨迹 | **自建为主**：与系统负责人固定工具、文档快照和奖励；模型与实际工具交互生成成功/失败轨迹 | 任务、快照、每步动作/观察、奖励、终止原因、模型和工具版本 | 先验证 20–50 条可重放任务及终局评分，再决定训练规模和算法 |
| 过程评估/奖励 | 标注过首错、工具参数和证据质量的轨迹 | **自建标注**：从实际运行结果抽样，双人试标并记录分歧 | 轨迹 ID、步骤、判断、错误类别或不确定、标注依据 | 先双人试标 30–50 条；先评估一致性，再决定是否扩展或训练 PRM |

规模是试运行目标，不是现成数据量或效果承诺。QASPER 和 LongDocURL 是第一轮候选，但前者要按许可使用，后者先核验许可再决定是否纳入外部评测；FinQA/TAT-QA 可在表格计算成为近期重点后补充。公开测试集与自建留出集只用于评测；按源文档和模板划分，避免训练泄漏。分别核对公开数据用于训练、再分发的许可及底层文档条款。

### 一条自建轨迹（SmartDoc 改造示意）

下面的合同流程是 SmartDoc 的数据构造示意，不是任何一篇论文的原始样本：用户问“两份合同的续约周期有什么不同”；系统分别检索 A、B 的续约条款，读取返回的页码和文本，再比较并带证据回答。每次记录工具名、参数和真实返回；如果 B 未检索到，示范应继续检索或说明证据不足，而不是编造页码。JSONL 结构见[数据样例](../data/examples/README.md)。

**CoT 和损失边界。** 可保存简短计划、可核验决策说明、工具动作、真实观察和证据；隐藏思维链不是必需标签。工具观察参与上下文，但一般不作为助手生成目标；训练掩码须由训练代码实现并测试，不能假定框架自动处理。

## 近期执行

1. 与系统负责人确定首批文档类型、工具清单、参数、返回结构及版本；登记公开数据许可、版本和切分。
2. 用 QASPER 和 LongDocURL 各抽小批题核对答案和证据，确认能否映射到现有工具；同时自建少量文档与留出题。
3. 用同一工具接口制作并执行 50–100 条 SFT 候选示范；检查工具返回、答案、证据与文档版本，记录失败原因。
4. 在系统支持重置后验证 20–50 条任务能否复现；抽取 30–50 条轨迹双人试标，作为奖励和过程评测设计依据。

实际进度依赖工具可用性、标注人力和许可核验；先检查小样本质量，再决定是否扩到会议讨论的几万条。

## 简要总结

- **评测：许可允许的 QASPER + LongDocURL 外部评测候选 + 自建。** QASPER 用于答案和证据基线；LongDocURL 先核验许可后再决定是否纳入；自建少量文档隔离的留出题补拒答和执行过程。
- **SFT：自建轨迹为主。** 许可允许的开源训练集可做普通问答基线；文档工具示范由真实工具返回、教师候选和人工校验构造。
- **Agentic RL：自建环境和轨迹。** 固定文档、工具和参考答案，从模型交互生成轨迹；先用可验证的终局奖励。
- **过程评估：自建轨迹标注。** 在实际结果中标首错、参数和证据；验证标注质量后再考虑过程奖励模型。
