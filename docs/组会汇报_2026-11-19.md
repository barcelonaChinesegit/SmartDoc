# SmartDoc 数据调研讨论提纲

日期：2026 年 11 月 19 日

详细方法、来源和局限见[数据调研与构建方案](data_research_zh.md)，文献 PDF 见[本地索引](../papers/INDEX.md)。下面的数据量都是试运行建议，具体取决于工具、人力和数据许可。

## 先对齐我们要准备什么

我理解现阶段先搭一个不训练的文档智能体原型，所以数据侧要先能判断它回答对不对、证据找得准不准，以及中间工具有没有用对。后续如果要做 SFT 或 Agentic RL，再准备工具调用示范和可重放交互任务。

我这次重点选了几篇与这几件事直接相关的工作，想先讨论它们怎么落到我们的数据上。

## 评测：答案和证据分开看

**LongDocURL：不直接使用数据，参考评测流程。** 它做了一个长文档基准：2,325 道问答覆盖 396 份文档，分理解、数值推理、跨元素定位三类，证据可能来自正文、表格或图，约一半问题跨页。论文 Figure 2 的真实例子包括：问 2018 年使用动物最多的四个研究领域；问 2018 年非人灵长类动物主要来自哪个地区，答案是 `Asia`；以及根据“2018 年 EU-28 和挪威使用 1,080 万只动物”的段落找章节标题。我们参考它的任务拆分和证据类型，不直接把数据当训练轨迹。

对我们最有用的是按任务类型、证据类型和是否跨页组织评测；它的“定位”还包括从段落找标题，不能直接等同于我们需要的坐标定位，而且不可回答题很少，我们要另外补。

**QASPER：许可允许时直接使用问答数据，参考证据标注流程。** 它是 1,585 篇 NLP 论文上的 5,049 个问题。提问者先看摘要提问，另一组人阅读全文回答和标证据，答案可以是抽取、归纳、是/否或不可回答。Figure 1 的真实问题是 `Which retrieval system was used for the baselines?`，支持证据分布在第 3、4 节。它分别算答案和证据的 F1，并按论文切分数据。

我们可以先拿 QASPER 的测试划分跑通问答与证据评价，训练和测试也按文档分开。它适合论文阅读场景，但不是合同或表格的完整替代，证据也不能假定都有 PDF 页码；格式适配和许可仍需核对。

## 轨迹：一次真实工具执行应该怎么记录

**DocAgent：不直接使用数据，参考系统流程。** 它先把文档整理成有章节、页码和元素 ID 的树状目录，再让执行智能体根据问题读取相关内容；它还用了审查智能体交叉核对答案和记忆。附录真实案例中，Actor 读取 `9.1.1` 章节回答“2008 到 2015 年哪个 Hispanic 子群体信心提升最多”，Reviewer 又调用 `get_table_image(table_id: 0)` 检查图表。我们可以借鉴目录和按需读取：把“看目录、搜索、读页、回答或复核”各步的工具名、参数、实际返回和证据 ID 记下来。

这篇给的是系统设计，不是我们可以直接拿来训练的文档轨迹；论文实验用 MMLongBench-Doc 和 DocBench，但我们不直接复用其轨迹。多智能体、额外复核会增加调用成本，后面应和单智能体方案比较，不能先假定更好。

**ToolACE：不直接使用数据，参考合成和质检流程。** 它解决的是如何合成多样的函数调用数据。论文用 `get the weather forecast`、`get the stock price`、`send an email` 等 API 功能示例，生成单次、并行、依赖调用以及无需调用的对话，之后用规则和模型两层检查。对我们的启发是先固定实际工具 schema，再围绕单页检索、跨页依赖、多文档比较、澄清和失败重试生成示范。

有一个区别要说清楚：ToolACE 的工具角色可以模拟结果。我们自己的文档示范应尽量实际运行解析和检索工具，用真实返回填观察，再核验答案和页码，不能让教师模型直接编一个工具结果。

合同续约比较只是 SmartDoc 改造示意，不是 ToolACE 原文样本：模型应分别查 A、B 的条款，读取实际页码和内容，再比较并引用；如果 B 没搜到，应继续查或说明证据不足，而不是猜。

## RL 和过程评测：借鉴什么，不预设什么

这一部分的使用结论先说清楚：Search-R1、TRAJECT-Bench、ProcessBench 三篇都不直接拿原数据训练 SmartDoc，分别参考检索型 RL 环境、工具轨迹评测、过程首错标注。论文原文例子分别是 Search-R1 的 Britney Spears 多轮检索、TRAJECT-Bench 的 `GetAllIATA -> airportInfo` 依赖链、ProcessBench 的 `cos(568°)` 第 2 步首错。

**Search-R1：不直接使用数据，参考 RL 环境和损失处理。** 它研究让模型在回答过程中自己决定“要不要搜、搜什么、还要不要继续搜”。论文 Table 9 的真实问题是 `Curious is a women’s fragrance by a singer born in what city and state?`，模型依次搜索香水、Britney Spears 出生地和 McComb 所在地，最后回答 `McComb, Mississippi`。作者用 PPO/GRPO 和最终答案 exact match 奖励训练，并在策略损失和 KL 损失中遮蔽检索返回的 token；对我们来说，工具返回应进入后续上下文，但不应当成模型需要生成的目标。

我们的改造是把搜索环境换成文档解析、检索和读取工具。**SmartDoc 改造示意：** 只找到合同 A 的续约条款时，模型应该继续查合同 B，而不是直接回答；这不是 Search-R1 原文样本。先验证任务能不能重置、工具返回能不能复现，先用答案和证据做终局奖励，再通过实验决定是否加过程奖励。Search-R1 本身并没有证明过程奖励一定必要。

**TRAJECT-Bench** 专门解决“最终答案对了，但工具过程可能是错的”这个问题。它整理 1,228 个可执行工具和 5,670 个问题，构造并行调用和有依赖的顺序调用，轨迹规模约 3 到 10 个以上工具；同一轨迹还配一个直接问法和一个更自然、更隐含的问法。除了答案，它分别评估工具序列是否匹配、标准工具的覆盖程度、参数是否匹配，以及整条轨迹是否足以完成任务。顺序依赖需要结合具体轨迹检查，工具覆盖本身不代表顺序正确。

我们可以借鉴这些检查项，做文档任务的过程评测：解析器是否选对、页码参数是否合法、证据是否取到、跨文档比较是否先分别取证。但不同工具路径可能都合理，所以完全匹配只能作诊断，不能作为唯一正确标准。

**ProcessBench** 把过程评测变成一个很清楚的任务：给模型一条完整的数学解题过程，找出最早出错步骤；如果全程正确就输出 -1。它有 3,400 条专家标注样本，结论是现有过程奖励模型在更难题上泛化不足，而且最终答案正确不代表中间每一步正确。

我们的文档场景可以借鉴这个“首错”标注：从实际轨迹里找第一次明确错误，比如查错文档、参数指向错误页、误读工具返回、证据不足却作答。工具故障和多条合理路径会让标注更难，因此先做少量双人试标，看一致性，再决定要不要做过程奖励模型。

## 接下来怎么试

1. 先和负责系统的同学对齐首批工具、输入输出、文档版本，以及日志能否保存真实返回。
2. 核对 QASPER 的可用划分、LongDocURL 的评测许可，各抽 20–50 题试跑；自建少量文档题，补充不可回答、失败恢复与引用检查。
3. 系统工具可用后，先制作 50–100 条文档 SFT 候选示范，真实执行并检查工具调用、返回、证据和答案。
4. 环境能重置后，试 20–50 个可重放任务；从真实轨迹中抽 30–50 条双人标注首错，评估一致性，再决定是否扩量。

## 最后总结：每个阶段需要什么数据

1. **评测：许可允许的 QASPER + LongDocURL 外部评测候选 + 自建。** QASPER 先测答案与证据；LongDocURL 先核验许可再决定是否纳入；自建少量独立留出题，补拒答、工具故障和过程检查。
2. **SFT：自建轨迹为主。** 许可允许的开源训练集可做普通问答基线；工具调用示范用合成或授权文档、教师候选、真实工具返回和人工校验构造。
3. **Agentic RL：自建环境与轨迹。** 固定文档、工具和答案，从模型与环境交互产生轨迹；先做可验证的终局奖励。
4. **过程评估：自建标注。** 从实际轨迹标工具参数、证据和首个明确错误；标注质量可靠后，再决定是否训练过程奖励模型。

先小规模跑通和核验，之后再决定如何扩展到几万条。
